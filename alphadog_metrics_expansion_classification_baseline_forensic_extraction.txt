Source: lines ~11280-11340 of the same file (this session's own live analysis of the real

Confirmed real mechanism (from that session's direct code reading, paraphrased where it is
analysis rather than verbatim quote):
- computeRecencyBlendedRate does NOT compute a 0-1 probability. It computes an average RATE
  PER GAME (e.g. ~0.6-0.8 hits/game, ~1.0-1.5 total-bases/game for a typical MLB hitter) - the
  "recency_blended_rate_0_100" field name is acknowledged in that session as misleadingly
  named (it is a scaled average rate, not a percentage/probability, and CAN exceed 100,
  confirmed by a real observed data point: hitter-strikeouts recency_avg showing 110.48%,
  found to be mathematically valid for a cumulative stat, not a bug).
- Two distinct downstream probability models exist: hpFromCountModel (a Poisson/Negative-
  Binomial-style model, appropriate for count stats with real magnitude variation like
  total_bases: 0,1,2,3,4) and hpFromNormalModel (used for other stat types) - both take the
  average-rate output of computeRecencyBlendedRate and convert it into an actual P(X >= line)
  probability.
- Total_bases numerator, confirmed as a real weighted sum via that session's own code read:
  doubles x2 + triples x3 + home_runs x4 (+ singles x1, implied by definition though its
  explicit coefficient was not independently re-quoted in the excerpt captured this pass).
- A specific, real, root-caused bug is documented here: hits>=1 and total_bases>=1 are "the
  exact same event" (identical empirical rate at the >=1 threshold), yet were being run
  through different shrinkage/recency profiles (Profile B vs the OLD Profile C for
  total_bases before the 2026-07-19 fix in Section 5B above), producing cross-prop
  monotonicity violations that WORSENED from 40% to 97% by player tier - this exact 40%->97%
  figure is a directly quoted real measurement from that session's own diagnostic pass.
