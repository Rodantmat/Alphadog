CRITICAL OPERATIONAL KNOWLEDGE - READ BEFORE STARTING
============================================================
1. Individual worker calls can be long-running by design. A probe_timeout error (typically at ~40 seconds) does NOT mean a call failed - it usually means that worker is still working in the background. After a timeout, check that step's real output table (see the relevant LAYER section below) for genuine progress before concluding anything failed.
2. Architecture change, confirmed 2026-08-05: this task no longer calls board-runner, daily-context-runner, market-runner, scoring-runner, scoring-runner-matrix, or scoring-runner-part2 at all - those orchestrator "runner" workers and their internal callStage() chaining are no longer part of this task's call path. This task now calls each of the ~24 underlying compute workers directly, in the exact sequence given in LAYER 1-4 below, and owns all chaining/continuation/retry logic itself (see SELF-HEALING PROTOCOL below for exactly how). Confirmed via github_grep_file across all 24 directly-called worker files (2026-08-05): none of them use control.runner_locks or any LOCK_KEY pattern - that locking mechanism was specific to the old orchestrator layer and does not exist for these workers. Do not check control.runner_locks as part of this task's normal operation anymore; it will not reflect the state of these direct calls, and a lock-key table for these 24 workers should not be assumed or guessed.
3. Wait-and-recheck pattern: after triggering a call that doesn't return an explicit completion signal, wait roughly 60-90 seconds, then check that step's (or that layer's) real output table for fresh/advancing data. There is no fixed cap on how many checks this takes for a step with a continuation field - see SELF-HEALING PROTOCOL below for exactly how to run those to real completion.
4. Known historical bug pattern (fixed 2026-08-02, worth knowing in case a similar issue resurfaces): MLB's schedule API sets abstract_game_state/detailed_state such that a postponed-and-rescheduled game can still look "Final" if the wrong status field is checked. The authoritative, independent source for "what games are genuinely happening today" is calendar.game_calendar, which has explicit is_postponed and is_cancelled boolean columns - always filter on these directly rather than inferring from a generic status string. Relatedly, calendar.game_calendar also has is_live and is_pregame boolean columns which are the authoritative source for whether a specific game has actually started - do not infer "started" purely by comparing a scheduled game_time_utc to the current wall clock, since real games can start later than scheduled. A bug of exactly this kind was found and fixed in alphadog-v2-market-certifier.js on 2026-08-02 (its gameHasStarted() now checks is_final/is_postponed/is_cancelled/is_suspended/is_live instead of comparing game_time_utc to now). alphadog-v2-market-certifier.js is still called directly in this task (LAYER 3, steps 16 and 20) - if you see a similar symptom elsewhere, investigate with the same rigor before concluding it's a bug, and apply the same kind of minimal, surgical fix if confirmed.
5. Known timing-race pattern (confirmed real 2026-08-02, resolved by a single retry): the external PrizePicks scraper and this pipeline's board promotion step can race - triggering LAYER 1 step 1 (prizepicks-github-board) moments before a concurrent scrape finishes will promote a slightly-stale snapshot even though a fresher one lands seconds later. This is why LAYER 1's verification checks tomorrow's coverage specifically, and why a single retry of step 1 (not indefinite retrying) is the documented fix for that specific symptom.
6. HISTORICAL - no longer part of this task's active call path, kept only for audit trail: on 2026-08-04, a 45-minute market-runner stall was root-caused to callStage() (the old orchestrator runners' internal fetch-chaining function) having no timeout on its fetch() to downstream sub-workers, and all 6 orchestrator runner files were fixed with AbortSignal.timeout(90000) on that call. As of 2026-08-05 this task no longer invokes those orchestrator runners at all (see point 2 above), so that specific failure mode can no longer occur within this task. Do not spend time checking for it as part of normal operation; it's documented here only in case those runner files are ever reintroduced elsewhere in the system.
7. Continuation mechanics vary by worker and are NOT interchangeable - confirmed live 2026-08-05. Some steps resume via chain_id; at least one (step 24) resumes via request_id instead - using chain_id there silently restarts it from scratch on every call instead of resuming, which is the exact bug that broke this stage before. One step (step 27) derives its own internal batch ID from another step's (step 26's) chain_id and will find no data if given a mismatched one. Use the exact field name and value specified for each step in the LAYER sections below - don't assume they're all the same mechanism.

SELF-HEALING PROTOCOL - APPLIES TO EVERY STEP
============================================================
This task calls ~24 individual workers directly, in the fixed 29-call sequence in LAYER 1-4 below, and owns all chaining/continuation/retry logic itself - there is no orchestrator layer doing this for you, and no control.runner_locks table relevant to these workers (confirmed 2026-08-05, see CRITICAL OPERATIONAL KNOWLEDGE points 2 and 7 above). For a call with NO continuation field in its response (most calls in this sequence):
a. Trigger it. It may time out on your end (typically ~40 seconds) for longer-running steps - this does NOT mean failure, do not treat it as an error.
b. Wait ~60-90 seconds, then check genuine progress via that step's real output table (see the relevant LAYER section for what to check, and the end-of-layer verification queries).
c. If it looks fresh/complete, move to the next call in the sequence.
d. If it looks stale or incomplete, re-trigger that same call and re-check. Per the COMPLETION STANDARD above, keep retrying and re-checking as many times as needed, however long it takes - no call limit. Only treat it as a genuine gap needing investigation (per FIX PHILOSOPHY below) if you have specific evidence the data cannot legitimately appear no matter how many times you retry (e.g. the documented LAYER 1 step 1 tomorrow-coverage race, which resolves on a single retry or not at all - see CRITICAL OPERATIONAL KNOWLEDGE point 5), not simply because you've retried more than once.

For a call WITH an explicit continuation field in its response (steps 10, 24, 25, 26, and 27 - each one's exact field name and completion signal is called out in its step in the LAYER sections below):
a. Pick one identifier string for that step (chain_id or request_id - whichever field that specific step uses; they are not interchangeable, see CRITICAL OPERATIONAL KNOWLEDGE point 7) and reuse the exact same value for every call of that step.
b. Call it, then check the response for that step's specific completion signal.
c. If not yet complete, call again immediately with the exact same identifier value. There is no call limit - repeat as many times as needed, however long it takes.
d. Only move on to the next step in the sequence once you've independently verified that step's real completion signal (not just because a response came back without an explicit error) - for step 26 specifically, verify via the real output-table query given in that step's notes rather than trusting continuation_required alone.

If any step needed one or more retries or continuation cycles but the full 29-call sequence still finished completely, that's a genuine success - use status 'ALL_STAGES_COMPLETE_SELF_HEALED' (see LOGGING below), not BLOCKED_NEEDS_HUMAN.
