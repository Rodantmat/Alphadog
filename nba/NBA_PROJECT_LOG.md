## 2026-08-31 (cont'd 6) — RESOLVED end-to-end: real nba.com data now flows all the way to Postgres, no manual step required, ever

The person was firm: no manual UI clicking, ever ("the whole point is for me to do not run it manually") — a fresh-chat-only tool wasn't good enough either, since it depends on a connector reconnect the person has to remember to do. Built a permanent fix using only capabilities every NBA chat already has (`github_put_file`/`github_patch_file`, present since the very first commit this session):

- Added a `push` trigger to `nba-scrape.yml` scoped to one dedicated file, `nba/TRIGGER_NBA_SCRAPE.txt` — any commit that changes that file's content fires the scraper. No new tool, no connector reconnect, no manual click, ever again, for any future NBA chat.
- First real trigger via this mechanism: **hard-failed with a 30s read-timeout** calling `stats.nba.com` from a plain GitHub Actions runner with vanilla `requests`. Bumped timeout to 60s + 3 retries — **still 3/3 timeouts**. Routed through `PROXY_URL` (the same repo secret MLB's PrizePicks scraper already uses) — **still 3/3 timeouts, ruling out IP-based blocking entirely** (proxied and unproxied GitHub Actions IPs both hung identically).
- **Real root cause, confirmed**: TLS fingerprinting, not IP blocking. Plain Python `requests` has a recognizable JA3/TLS handshake that bot-management systems silently tarpit (accept the connection, never respond) rather than reject outright — exactly why MLB's own scraper uses `curl_cffi` (Chrome TLS impersonation) instead of `requests`. Switched `scrape_nba_stats_teams.py` to `curl_cffi` with `impersonate="chrome124"` — **worked on the very next attempt**: real `stats.nba.com` `leaguestandingsv3` response, HTTP 200, 30/30 teams, committed to `nba/data/nba_teams_current.json` + a meta file.
- One data-shape bug found and fixed in the same pass: `leaguestandingsv3`'s real response has no `TeamAbbreviation`/`TeamCode` column at all (came back empty for all 30 teams) — patched with a small, verified team-ID→abbreviation map (all 30 IDs cross-checked against the already-certified static fallback list, exact match).
- Rewired `alphadog-v2-nba-static-teams.js` to read this GitHub-committed file first (same Contents-API pattern `alphadog-v2-prizepicks-github-board.js` already uses for `prizepicks_mlb_current.json`), with the direct-`stats.nba.com`-from-Worker attempt and the certified static list kept as second/third fallbacks, in that order. One real bug found and fixed here too: the initial version requested GitHub's raw media type (`application/vnd.github.raw+json`) but then tried to parse the response as the base64-JSON envelope shape — fixed by requesting the standard `application/vnd.github+json` Accept header instead.
- **Triggered `run_job(target="NBA_STATIC_TEAMS_WORKER")` for real after each fix, verified against Postgres independently each time (not just trusting the worker's own report)**. Final, confirmed-correct state: `source_key: NBA_GITHUB_COMMITTED_STATS_NBA_SCRAPE`, `fetch_method: github_committed_json`, `nba_ref.teams` → 30/30 active (verified via direct `SELECT COUNT(*)`), `nba_ref.team_aliases` → 162 active rows.
- **One small, honest, non-blocking nuance recorded rather than glossed over**: `teamHasRealChange()` only updates a row's `source_key` when a real field actually changed — since all 30 teams' data was already correct from the earlier fallback seed, 25 of 30 rows still show their older `STATIC_SEED_FALLBACK_AFTER_FETCH_ERROR` source_key even though this run verified them against the real source too; only the 5 rows with a genuine diff (none, in this case — actually 5 were "written" due to matching against a slightly different current-Postgres snapshot at the time) got the new source_key stamped. Data is fully correct either way; the source_key column just isn't a perfectly reliable "last verified against which source" audit trail as currently written. Worth a small dedicated fix later (e.g. always stamp source_key + a separate `last_verified_at` even on no-op rows) but not urgent.

**Full loop now working, repeatably, hands-off**: any future NBA chat can re-run the teams pipeline end-to-end — real nba.com data, no manual GitHub UI step, no tool-list/connector dependency — by (1) bumping `nba/TRIGGER_NBA_SCRAPE.txt` via `github_put_file`, (2) polling `github_list_workflow_runs`/`github_get_workflow_run_log` until "NBA Static Data Scraper" succeeds, (3) calling `run_job(target="NBA_STATIC_TEAMS_WORKER")`, (4) verifying independently against `nba_ref.teams`/`nba_ref.team_aliases`. This exact 4-step pattern (trigger-file push → GitHub Actions scrape with curl_cffi → committed JSON → Worker reads via Contents API → Postgres) is the template for every future nba.com-sourced NBA worker (players next).
